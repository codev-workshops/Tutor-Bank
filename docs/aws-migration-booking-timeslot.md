# Booking and TimeSlot AWS migration

## Scope

With `DB_MODE=aws`, only `Booking` and `TimeSlot` records are stored in
DynamoDB. PostgreSQL remains the default when `DB_MODE` is unset or
`postgres`. All other Prisma models continue to use the real PostgreSQL
client.

The finite Prisma call shapes covered by this migration are:

### `src/app/api/bookings/route.ts`

- `tx.timeSlot.findUnique({ where: { id: slotId } })`
- `tx.booking.create({ data: { studentId, tutorId, slotId } })`
- `tx.timeSlot.update({ where: { id: slotId }, data: { isBooked: true } })`
- `prisma.booking.findMany({`
  `where: role === "TUTOR" ? { tutorId: userId } : { studentId: userId },`
  `include: {`
  `student: { select: { id: true, name: true, email: true } },`
  `tutor: { select: { id: true, name: true, email: true } },`
  `slot: { select: { id: true, date: true, startTime: true, endTime: true } }`
  `},`
  `orderBy: { createdAt: "desc" }`
  `})`

### `src/app/api/bookings/[id]/route.ts`

- `prisma.booking.update({ where: { id }, data: { status } })`
- When status is `REJECTED` or `CANCELLED`:
  `prisma.timeSlot.update({`
  `where: { id: booking.slotId },`
  `data: { isBooked: false }`
  `})`

### `src/app/api/tutors/[id]/slots/route.ts`

- `prisma.timeSlot.findMany({`
  `where: { tutorId: id, date: { gte: new Date() } },`
  `orderBy: { date: "asc" },`
  `select: { id: true, date: true, startTime: true, endTime: true, isBooked: true }`
  `})`
- `prisma.timeSlot.create({`
  `data: { tutorId: id, date: new Date(date), startTime: new Date(startTime),`
  `endTime: new Date(endTime) }`
  `})`

### `src/app/api/tutors/[id]/route.ts`

- `prisma.user.findUnique({`
  `where: { id, role: "TUTOR" },`
  `select: {`
  `id: true, name: true, email: true, bio: true, hourlyRate: true,`
  `subjects: { select: { subject: { select: { id: true, name: true } } } },`
  `timeSlots: {`
  `where: { isBooked: false, date: { gte: new Date() } },`
  `orderBy: { date: "asc" },`
  `select: { id: true, date: true, startTime: true, endTime: true }`
  `}`
  `}`
  `})`

The AWS delegates reject any argument shape outside this list with an
explicit unsupported-in-AWS-mode error.

## DynamoDB data model

The tables are `${DYNAMODB_TABLE_PREFIX}TimeSlot` and
`${DYNAMODB_TABLE_PREFIX}Booking`; the prefix defaults to the empty string and
is applied consistently. Both tables use `id` (string) as their partition key,
use PAY_PER_REQUEST billing, and are created idempotently.

IDs are cuid-shaped values generated by the adapter. They are not generated
by Prisma, and tests must assert only their shape, never an absolute value.

All `DateTime` values (`date`, `startTime`, `endTime`, `createdAt`, and
`updatedAt`) are stored as fixed-width ISO-8601 UTC strings from
`Date.toISOString()`. Reads convert them back to real `Date` instances.
Lexicographic ordering therefore matches chronological ordering.

`TimeSlot` has GSI `tutorId-date-index` with `tutorId` as HASH,
`date` as RANGE, and ALL projection.

`Booking` has GSIs `tutorId-createdAt-index` and `studentId-createdAt-index`
with the named id field as HASH and `createdAt` as RANGE, plus `slotId-index`
with `slotId` as HASH. All use ALL projection.

Defaults are `status: PENDING`, `isBooked: false`, and generated timestamps.
An update always advances `updatedAt`; if wall-clock time is not strictly
greater than the stored value, it is bumped by one millisecond.

The `Booking.slotId` uniqueness constraint is emulated by checking
`slotId-index` before create and throwing a Prisma-shaped `P2002` error. This
check is not atomic, unlike PostgreSQL's unique constraint.

In-memory ordering uses the requested primary key and then `id` ascending as
a deterministic tie-breaker. Primary-key reads use `GetItem` with
`ConsistentRead: true`. GSI reads are eventually consistent: after a GSI hit,
the item is re-read consistently by primary key, and GSI queries are retried
before concluding that no item exists.

## Emulated versus native behavior

| Area | PostgreSQL behavior | AWS-mode behavior |
| --- | --- | --- |
| Storage | Booking and TimeSlot rows | Booking and TimeSlot DynamoDB items |
| IDs | Prisma `cuid()` default | Adapter-generated cuid-shaped IDs |
| Dates | Native `DateTime` columns | ISO-8601 UTC strings on disk, `Date` objects in results |
| Booking uniqueness | Atomic `slotId` unique constraint | Pre-create GSI check; not atomic |
| Transactions | One database transaction | Callback uses the hybrid client; no cross-store atomicity |
| Notifications in booking POST/PATCH | Same PostgreSQL transaction where applicable | PostgreSQL notification write cannot roll back a DynamoDB write |
| PATCH path | Existing PATCH is non-transactional | Existing PATCH remains non-transactional |
| GSI consistency | PostgreSQL reads are transactionally/currently consistent | GSI reads are eventually consistent, with consistent re-reads and retries |
| Ordering | Database ordering | In-memory ordering plus `id` ascending tie-break |
| Booking relations | Foreign keys and cascading deletes | Cross-store lookup; required student/tutor/slot relations use inner-join semantics and incomplete rows are dropped from lists |
| User nested slots | PostgreSQL relation selection | User lookup stays in PostgreSQL; `timeSlots` is stripped, read from DynamoDB, then merged |
| Unsupported calls | Prisma supports its normal API | Only the documented call shapes are supported; others fail loudly |

The required authentication parity case is also intentional: with no session,
the current booking POST returns HTTP 500 with `{"error":"Internal server error"}`
because `requireAuth()` throws and the route's generic catch handles it. This
migration does not add a 401/403 path.

The e2e project runs under `next/jest` with a Node test environment and a
separate setup file. The setup file mocks only
`next-auth`'s `getServerSession`; Prisma remains real in both modes. The
default transform cannot load the ESM-only `@auth/prisma-adapter` package
(`Unexpected token 'export'` while importing `src/lib/auth.ts`), and then
cannot call the ESM credentials provider through the CommonJS transform.
A direct attempt with the default transform also reaches Prisma's real
dynamic ESM query compiler and fails on
`query_compiler_fast_bg.postgresql.mjs` with `Unexpected token 'export'`.
Therefore the config uses two minimal module-loading harness shims:
`prisma-adapter-bridge.js` exposes the adapter-shaped export and
`credentials-provider-bridge.js` exposes the provider-shaped export. They are
not behavioral test stubs, do not mock Prisma or authentication behavior, and
exist only to let Jest load the real application modules. The config retains
the smallest ESM-compatible `ts-jest` transform and
`NODE_OPTIONS=--experimental-vm-modules` needed to execute the real Prisma
client.
